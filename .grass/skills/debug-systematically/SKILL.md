# 排查：先定位再动手

修错的根因比不修还糟——症状被压下去，下个月换个地方冒出来。

## 一、复现

没有稳定复现就没有排查。拿到这几样：

- 触发它的最小输入
- 实际输出（完整，不要截断）
- 期望输出

报错要**完整**的堆栈和原文。截断的报错看不出调用链。

## 二、缩小范围

用排除法二分，别一上来就通读代码：

1. **找到边界**：问题从哪一步开始出现的？往前一步还是好的
2. **二分**：把可疑的地方一个个注释掉或换成常量，看症状变不变
3. **打印中间状态**：在关键节点打日志，别只在入口和出口打

## 三、几个能省时间的判断

- **先怀疑自己刚改的**：如果问题是刚出现的，回看最近的改动
- **是环境还是逻辑**：换台机器、换配置还复现吗？复现不了就是环境
- **是不是本来就坏的**：把改动 stash 掉跑一遍。存量问题不要背到自己头上
- **错误信息往往就是答案**：`Cannot find name 'x'` 是真找不到，
  `UV_HANDLE_CLOSING` 那是 libuv 断言，跟你的业务逻辑没关系
- **先看日志级别**：很多"没反应"是没开 debug 日志，不是没发生

## 四、确认根因

满足这三条才算找到根因：

1. 能解释**全部**现象（不是只解释一半）
2. 能稳定复现
3. 改掉它，症状消失

只满足前两条，第三条验证不了，说明找错了。

## 五、修

- 修根因，不是修症状。症状是"崩溃"，根因是"空指针"
- 修完补一个能覆盖这个场景的测试，防止它再回来
- 同类问题一并检查：同一个根因在别处是不是也有

## 六、别做的事

- 不要靠"多试几次"或者加重试掩盖问题
- 不要为了让测试变绿去改测试的断言——先问自己是不是测试写错了
- 不要在没定位之前就动手改
