# 改代码：从读到验

改代码最常见的失败不是写错，是**没验证就宣布完成**。
这个技能把「验证」做成流程的一环，而不是想起来才做。

## 一、先读，别先猜

动手前把相关代码读完，至少确认：

- 改动的函数在哪、谁调用它（`grep` 一下调用点）
- 有没有别的路径也会走到这里
- 项目里同类的事是怎么写的——**照着现有写法走**，别自创一套

路径越界、编码约定、分层规矩这些是硬约束，不看 CLAUDE.md 就改，多半要返工。

## 二、动手

- 改动要小。改一处能解决就别改三处
- 注释讲「为什么这么写」，不重复代码字面意思，简短
- 变量名用完整英文单词，不用缩写
- 新功能先想设计模式：单一职责、开闭原则、依赖倒置、封装变化
- 并发改文件时，涉及 `mutatesFiles` 的工具要声明，否则同一文件两次写会互相覆盖

## 三、验证（这一步不能省）

按改动范围选命令，全都要跑：

```bash
npm run typecheck    # 类型
npm run test:unit    # 单元测试
npm test             # 端到端
```

改了 `src/` 下的文件，对应的 `test/` 下必须有测试文件。

**测试失败先分清是谁的问题**：是这次改动弄坏的还是本来就坏的？
不确定就先把改动 `git stash` 掉再跑一遍同样的命令，对比结果——
别把存量失败算到自己头上，也别把自己的失败推给存量。

## 四、确认真的改到了

测试通过不等于改对了。再确认一遍：

- 产物真的在：`ls -la` 看时间戳
- 行为真的变了：跑一次实际场景，不是只跑单测
- 没有顺手改坏别的：`git diff --stat` 看改动的文件清单，
  跟预期对不上就停下来查

## 五、收尾

- 改完自检：注释是否还成立、有没有留下调试代码、变量名是否还准确
- 文档跟着改：新增的配置项要同时改 `src/config.ts` 的 schema 和 `.env.example`
- **不要顺手提交**。提交要用户明确要求；提交信息用中文，
  格式 `<type>(<scope>): <subject>`

## 六、禁止事项

- 禁止用脚本或命令批量改文件。所有改动必须用编辑工具
- 禁止 `git checkout`，禁止任何可能破坏 git 历史的操作
- 推送必须先问过用户
- 改数据库表结构不能直接执行，给出 SQL 让用户自己跑
